# ResolveAI 轻量化会话上下文设计

## 1. 设计目标

电商客服的常见咨询只有 3–5 轮。Agent 需要记住本次咨询中已经说过的商品、订单线索、用户诉求和客服答复，但不需要为这类短对话维护四层独立的记忆体系。

本阶段采用 **当前会话原始消息 + 按需查询 Commerce Service**。`Message` 是会话上下文的唯一来源；LangGraph Checkpointer 只负责单次运行的中断恢复，不作为跨轮或跨会话知识库。

| 数据 | 用途 | 本阶段处理 |
| --- | --- | --- |
| `Message` | 保存用户与客服的原始发言，供同一会话后续轮次读取 | 使用现有表与上下文加载器 |
| LangGraph Checkpointer / `ToolExecution` | 保存运行状态和工具调用结果，供失败恢复与重试判断 | 保留现有机制，按 `run_id` 隔离 |
| Commerce Service | 提供订单、物流、库存、退款、售后单等当前业务事实 | 每次需要时通过 Tool 查询 |
| `ConversationSummary` / `CustomerMemory` | 原四层方案中的摘要与客户长期记忆 | 暂不生成、写入或注入 Prompt；已有表暂作兼容保留 |
| `ServiceTicket` / `ServiceEvent` | 原方案中的服务经历记忆 | 不作为记忆系统建设；售后状态使用现有 Commerce 售后接口 |

## 2. 每轮处理流程

1. 接收新消息时，确认调用方身份及其对 `conversation_id` 的访问权，并持久化用户原话。
2. `prepare_context` 读取**同一会话**中早于本次触发消息的用户和客服消息，按稳定的会话内顺序排列，再加入系统提示词和本轮消息。正常 3–5 轮会话直接使用原文，不调用模型生成摘要。
3. Agent 如需判断价格、库存、订单、物流、退款或售后进度，通过 Commerce Tool 查询；会话中曾提及的状态只可作为查询线索，不能当作当前结果。
4. 保存最终客服答复。后续轮次重新从原始消息构建上下文；运行恢复则继续使用对应 `run_id` 的 checkpoint。

```text
同一会话的历史 Message + 本轮用户 Message
                    ↓
              prepare_context
                    ↓
               LangGraph Agent ──按需──> Commerce Tool
                    ↓
              客服答复写入 Message
```

上下文加载只包含已确认完成的历史答复和本轮触发消息，不能混入其他客户、其他会话或并发中尚未完成的答复。同一运行重试时应复用触发消息，避免重复加入本轮用户发言。

## 3. 上下文边界与可靠性

- **短会话默认保留原文。** 当前 `_conversation_history` 最多读取此前 10 轮已完成的问答（20 条消息），足以覆盖典型 3–5 轮会话。这个条数只是防止异常长会话无限增长的上限，不代表已控制 Token；上线前应以实际模型的输入预算验证包含系统提示词和工具结果后的长度。
- **顺序必须确定。** `Message.seq` 在会话锁下分配。历史读取只选提问和答复都早于本轮触发消息的成功运行，再按消息顺序输出；相同时间戳不会改变顺序或遗漏消息。并发提交时，尚未完成的问答不会进入本轮上下文。
- **超长输入按预算裁剪。** 若少数会话或单条消息超出模型预算，优先保留本轮问题、最近轮次和完成当前任务所需的线索；必要时提示用户补充被裁剪的早期信息。此路径先通过可测的裁剪规则实现，不引入异步摘要任务。
- **原话和业务数据各司其职。** 客户说过的偏好或意图仅在当前会话中按原话使用；订单和售后结果以 Commerce 当前响应为准。工具不可用时说明无法确认，不能依据聊天历史猜测业务状态。
- **恢复不扩大记忆范围。** Checkpointer 的作用是恢复当前 `AgentRun`。工具是否已生效仍由 `ToolExecution` 和业务系统结果判断。退款结果写工具使用幂等状态转换；结果不明时先查询 Commerce，再决定是否重试。

## 4. 本阶段不建设的能力

不启动自动客户画像、向量检索、跨会话偏好抽取、摘要更新或独立服务经历事件流。现有 `ConversationSummary` 和 `CustomerMemory` 只是已迁移的表，并不表示相关功能已启用。用户在新会话中提到以前的订单或售后事项时，Agent 应从 Commerce 查询可授权的当前数据；无法从业务系统取得的旧聊天内容，不自动作为新会话上下文。

只有在真实会话数据显示原文上下文经常超预算，或明确需要跨会话复用客户稳定偏好时，再分别评估摘要或显式保存偏好的能力。新增能力须有独立的收益、隐私和维护成本评估，不能因为预留了表就默认启用。

## 5. 落地顺序与验收

1. 已修正历史消息的确定顺序和触发边界，并覆盖同时间戳、并发提交、重试时不漏消息、不重复本轮消息、不跨客户或会话读取。
2. 用 3–5 轮的商品咨询、订单查询和售后跟进样例，确认上下文包含完整原话，且当前业务状态来自 Commerce Tool。
3. 记录实际输入 Token 分布；只有观测到超预算场景时，增加确定性的上下文裁剪并验证本轮诉求不会丢失。

当前代码已实现原始消息持久化、最多 10 轮已完成问答的历史加载、按运行隔离的 checkpoint、只读 Commerce Tool 和一个售后单退款结果写工具。Token 预算控制仍待实现；本设计不把它描述为已上线能力。
